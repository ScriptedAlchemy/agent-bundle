Bind a CLI or MCP route's `inputSchema` to a schema declared in another module: `export const inputSchema = statusInputSchema`, imported from a relative module inside the project (through any number of `export const` alias hops; `.js` specifiers map onto their `.ts`/`.tsx` source), is resolved statically — no module is executed — and parsed in the declaring module's scope under the unchanged bounded grammar, so a `src/cli/**` command and an MCP tool share one schema instead of each carrying a copy. The route graph normalizes every statically read schema once into a `RouteContract` (`id` = `contract:<module>#<binding>`, `input`, `origin`, `routes`), listed as `contracts` in `agent-bundle inspect --routes` and the Workbench Routes page and named by each route as `route.contract`; the argv grammar, the static MCP `inputSchema`, and the route manifest are projections of it. The `const` string-literal form of static route `config` (`AB4806`) now follows the same alias hops across any number of relative modules. On a CLI route a reference the resolver cannot follow — a bare specifier, a module outside the project, a missing `export const`, a non-`const` binding, a dynamic initializer — is `AB4838` naming the import chain and the boundary, and a cyclic chain is `AB4839`; grammar violations inside a resolved schema stay `AB4814` with the position qualified by the declaring module, and MCP, script, and event routes with an unresolvable schema stay silent as before. `resultSchema` may be imported the same way (#593)
